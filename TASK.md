# Build task for Tezz POS (demo-ready v1). Read docs-POS_PLAN.md for context (sections 12-14 are the spec).
Monorepo layout:
- api/ : Python 3.12 FastAPI + SQLAlchemy 2 + Postgres (psycopg) ; Alembic optional (create_all is fine). pytest tests using SQLite or a test Postgres (prefer SQLite via env DATABASE_URL so tests run without docker).
- web/ : Next.js 14 (App Router, TypeScript) PWA cashier UI, Tailwind CSS. Premium look: dark sidebar, clean cards, large touch buttons, brand "Tezz POS" with lightning mark, accent emerald/amber. English UI with an Urdu toggle for key labels (simple dictionary).
- docker-compose.yml: services db (postgres:16), api (port 8000 internal), web (Next.js production build, port 3000 internal), and a single entry via web proxying /api to api (Next rewrites). Host port from ${APP_PORT:-8120} -> web 3000. Also expose API docs through web at /api/docs (rewrite). api seeds demo data on startup if DB empty.
- .env.example, README.md, docs/HOW_TO_TEST.md, docs/api-guide.md, postman/tezz.postman_collection.json, .github/workflows/ci.yml (pytest + web build).
Backend features:
- Hierarchy: Company > Branch > Terminal; Users (roles: owner, manager, cashier) with PIN login (JWT). API keys (tz_test_ prefix) per company for public API, header Authorization: Bearer.
- Full CRUD under /api/v1 for: branches, terminals, users, categories, products, modifier-groups (with modifiers), deals, taxes, customers, floors, tables, kitchen-stations, payment-methods, orders (with lines and line modifiers), payments, shifts, webhooks, api-keys. Use a generic CRUD router helper to keep code small. Pagination ?limit&offset, filter ?updated_since.
- Actions: POST /orders/{id}/pay, /void, /refund; POST /shifts/{id}/close ; GET /shifts/{id}/z-report ; GET /orders/{id}/receipt (JSON + HTML at /receipt.html with all SRO 1006 fields, FBR fiscal number, QR code (use python 'qrcode' lib -> SVG), Re.1 POS fee line, "Verify via Tax Asaan / SMS 9966" text).
- Offline sync: POST /api/v1/sync/batch accepts orders with client_uuid (idempotent upsert), GET /api/v1/sync/status?terminal_id= returns counts and per-order server/fiscal/erp status. POST /api/v1/fiscal/{order_id}/retry and /api/v1/erp/{order_id}/retry.
- Adapters with an interface: fiscal (MockFBR: returns invoice number like "123456-DDMMYYHHMMSS-0001"; configurable failure rate via env FISCAL_MOCK_FAIL_RATE; real FBR IMS adapter class with sandbox URL https://esp.fbr.gov.pk:8244/FBR/v1/api/Live/PostData building the exact IMS JSON fields, unused unless FISCAL_PROVIDER=fbr) and ERP (MockERP, OdooAdapter skeleton using JSON-RPC execute_kw for product.product read and pos.order create_from_ui, unused unless ERP_PROVIDER=odoo). Rs.1 POS fee added to each paid order.
- Webhooks: store subscriptions; on order.paid send HMAC-SHA256 signed POST (best-effort, errors logged).
- OpenAPI tags and descriptions good quality, /api/docs (Swagger) and /api/redoc.
- Seed demo: company "Lahore Karahi House" (Gulberg, Lahore; NTN 1234567-8, STRN 3277876123456, PRA), branch Gulberg + branch DHA, 2 terminals, users: owner PIN 1111, manager 2222, cashier 3333. Categories: Karahi, BBQ, Rice, Naan & Roti, Deals, Drinks, Desserts. ~30 products with PKR prices (Chicken Karahi Half 1,450 / Full 2,700, Mutton Karahi, Seekh Kabab, Chicken Tikka, Malai Boti, Chicken Biryani, Kabuli Pulao, Plain Naan 60, Garlic Naan 120, Roghni Naan, Raita, Salad, Kheer, Gulab Jamun, Lassi, Mint Margarita, Soft drink 1.5L, Kashmiri Chai...). Modifier groups: Spice level (Mild/Medium/Hot), Karahi size (Half/Full), Extras (Extra Cheese Rs.150, Extra Raita 100), Naan type. Deals: "Family Deal" (Full Karahi + 4 Naan + 1.5L drink Rs.3,499), "Student Deal". Tax: PRA 16% card 5%? Keep simple: tax 16% cash, 5% card/digital (PRA reduced rate for card, mark as configurable). Floors: Ground (T1-T8), Rooftop (R1-R6). Kitchen stations: Karahi, BBQ, Tandoor, Drinks. Payment methods: Cash, Card, Raast QR, JazzCash, Easypaisa. ~25 sample orders over last 3 days, mixed statuses: most synced+fiscal ok, 3 fiscal failed (reason "FBR gateway timeout"), 2 ERP pending, plus 3 orders that the seed marks as "client pending" are NOT on server (provide them as /api/v1/demo/unsynced-orders JSON so the web app can preload them into IndexedDB on first run for the demo). One open shift, one closed shift with Z report.
Web features (pages):
- /login : PIN pad, branch/terminal picker.
- /pos : cashier screen. Left: categories, product grid with search; modifier dialog; deals; cart on right with qty, notes, discount, order type (Dine-in/Takeaway/Delivery), table picker, customer phone; Pay dialog (Cash with change calc, Card, Raast QR, JazzCash, Easypaisa, split). Orders ALWAYS saved to IndexedDB first (use 'idb' lib), then sync loop pushes to /api/v1/sync/batch every 10s when online. Show online/offline badge and pending count in header. After pay show receipt (fetch HTML receipt when synced, else local receipt marked "OFFLINE MODE - fiscal number pending").
- /tables : floor plan grid with table status (free/occupied), click to open order.
- /kds : kitchen display, tickets by station, Start/Done buttons, auto-refresh.
- /orders : order history with filters.
- /sync : Sync Status page: counters Synced/Pending/Failed, table with order no, time, amount, chips for Server/FBR/ERP status, error text, Retry and Retry all buttons, "Simulate offline" toggle for demo (forces offline in the client).
- /shifts : open/close shift, cash count, Z report view.
- /admin : simple tabs to list/create products, categories, modifiers, tables; API keys page showing demo key; link to API docs.
- manifest.json + service worker (basic caching of app shell) for PWA.
Quality: pytest covering CRUD, sync idempotency, pay + fiscal mock, receipt fields, z-report. `npm run build` must pass. Keep secrets in env only. Everything MIT/Apache/BSD deps. Do not run anything outside this repo directory. Do not push to git; the operator commits.
